# Великая реформа труб II

База: 0.3.332 / bc1da5bc. Пакет задач, runtime не изменён. [Карта пакетов](<00 — Карта пакетов.md>).

Все найденные вопросы валидации, оптимизации и жизненного цикла труб собраны здесь. D-PIPE2 остаётся отложенным; PERF-001/13/14 ранее не выбраны для реализации. Для жидкостных/энергетических труб новых дефектов этот пакет не утверждает: общие изменения требуют проверки затронутых типов, а не их попутного редизайна.

## PIPE-II-1 — общий лимит вида предмета на узел

Источник: A3. Приоритет P2. Подтверждение: нативный серверный тест + прямое уточнение автора «Общий лимит на весь узел».

В [ItemRouting](../src/main/java/com/gonzotech/machines/network/ItemRouting.java) tickExtract вызывает pushItems для каждой грани, а Map perItem создаётся внутри pushItems. Поэтому каждая грань получает новый лимит одного вида. Общий количественный бюджет не решает это расхождение.

Воспроизведение: один first_item_node, два доступных источника одинаковых предметов на разных гранях, доступный получатель. В тесте один вызов переместил 2 предмета при perItemCap=1; суммарное число осталось 10. Это превышение пропускной способности, не дюп количества.

Задача: единый счётчик по Item на один проход узла, общий для всех входных граней. Сохранить отдельно общий бюджет и существующие правила момента запуска. Не объединять лимиты независимых узлов и не менять баланс-константы.

Приёмка: 1/2/6 входных граней; одинаковые и разные Item; заполненный получатель; частичный приём; неудачные попытки не съедают успешную квоту; независимые узлы сохраняют свои лимиты. Проверить не только return moved, но и фактическую сумму источников/получателей.

## PIPE-II-2 — фильтр не должен обходить всю сеть без работы

Источник: A5. Приоритет P2, оптимизация. Подтверждено исходниками; TPS не измерен.

В [ItemFilterRouting](../src/main/java/com/gonzotech/machines/network/ItemFilterRouting.java) collectSinksFromCarrier выполняется до проверки пустоты/отсутствия работы; его очередь не ограничена общим бюджетом BFS обычных труб. Пустой фильтр способен выполнять бесполезный полный обход длинной сети.

Первый ограниченный шаг: дешёвое определение отсутствия доступной работы до дорогого поиска, без полного сканирования сети ради самой проверки. Следующий этап: общий учёт стоимости поиска фильтров и обычных сетей; объединение с PIPE-II-5 только при выборе deferred-работы.

Приёмка: пустой фильтр и большая сеть; пустые/непустые соседние источники; pass/reject; блокированные стороны; смена шаблонов и redstone; выгруженная граница. Измерять посещённые узлы/проверенные рёбра и серверное время, а не только итог перемещения.

## PIPE-II-3 — повторная валидация общих участков маршрутов

Источник: PERF-001/13. Приоритет P2, оптимизация; реализация ожидает выбора автора.

liveSinks повторно проверяет пути к получателям. Бюджет 2048 узлов поиска не ограничивает автоматически всю последующую стоимость проверки маршрутов, особенно для нескольких источников и длинных общих участков.

Задача: измерить стоимость, затем переиспользовать результат проверки общих сегментов в пределах безопасной ревизии топологии. Не подменять валидность одним TTL: разрыв/замена трубы или контейнера в том же тике должен запрещать следующий перенос по старому пути.

Приёмка: общий длинный ствол с ветками; несколько входов; разрыв и восстановление в том же тике; изменение режимов/граней; замена BE по той же координате; выгрузка чанка. Сравнить холодный и прогретый кэш, счётчики обходов и задержку доставки.

## PIPE-II-4 — жизненный цикл кэшей

Источник: PERF-001/14. Приоритет P2. Структурный риск удержания мира; heap-утечка измерением не подтверждена.

Цепочка TOPO_CACHE → CachedSinks → Sink → Container/BE → Level способна удерживать мир через значение WeakHashMap. Слабого ключа недостаточно.

Задача: явная очистка на остановке сервера/выгрузке уровня; ревизия сильных ссылок в записях. При переходе к адресам повторно разрешать текущего владельца и проверять identity/loaded-состояние. Очистка одного мира не должна сбрасывать чужую рабочую сеть.

Приёмка: несколько последовательных запусков интегрированного сервера в одном JVM; выгрузка/создание миров; отсутствие старых BE в записях; размеры кэша после остановки; heap/ссылочный анализ. Не объявлять исправление доказанным одним System.gc().

## PIPE-II-5 — продолжение больших BFS

Источник: D-PIPE2, остаток PERF-001/3. **Отложено.** Исправленный complete=false не переоткрывается.

Незавершённый обход может отбрасываться и повторяться с начала: дальние получатели не получают гарантии достижения. Здесь обоснован архитектурный этап — сохраняемый фронт поиска, справедливый общий бюджет и корректная отмена устаревшего поиска.

Перед реализацией отдельно выбрать политику публикации частичных результатов; она ранее не утверждена. Не считать частично найденную сеть полной. Прогресс поиска не может разрешать перенос по уже разорванному маршруту.

Приёмка: сеть больше бюджета; конкурирующие старты; несколько миров; нагрузка фильтров; изменение топологии во время поиска; гарантированный прогресс при стабильной сети без принудительной загрузки чанков. Задать измеряемый бюджет работы и предельные задержки после профилирования, не выдумывать новые числа баланса.

## Общие инварианты и доставка

- Сохранять предметы и радиационные sidecar-данные, физическую идентичность владельцев, double chest 54 slots, loaded-only, лимиты слотов, корректный simulate и DAG-защиту перемещений. Проверять сумму во всех фактически участвующих хранилищах.
- Не возвращать старый LAST_INSERTED или глобальный запрет независимых входов. Сохранять разрешённое продвижение по сети в одном тике.
- Пучки новых типов также используют ограниченный кэш геометрии с полным ключом; не пересобирать shape на каждый запрос. Не менять PNG, down UV узлов или механику mastery ради routing.
- Минимальные регрессии: item_parallel_inputs, double_chest_routing, item_bfs_budget, item_loaded_chunks, routing_cache, pipe_routing_tail/perf, slot_capacity, composite_bundle; дополнительно реальные GameTest для новых случаев.
- При runtime-патче сверить CAPABILITIES, MACHINES, MULTIBLOCK при затронутых портах, RULES при новом утверждённом правиле, CURRENT/HISTORY/AUDIT. PERF-001/13/14 и D-PIPE2 остаются исходными ID, не закрывать их одной записью «реформа готова».
