# Меловая доска: серверная проверка открытий и мультиплеерная совместимость

**Статус:** документирует patch `12166f1` и последующую корректировку лимита рисунка.

**Коротко для игры:** нормальная работа доски не должна измениться. Игрок, как и раньше, заполняет пустые ячейки, может домножать или делить части формулы и нажимает кнопку получения открытия. Отличие только в том, что сервер теперь самостоятельно убеждается: присланная формула относится к *текущему* открытию игрока, а не является произвольной формулой, которую прислал изменённый клиент.

Этот файл намеренно подробный. Он нужен как карта изменений, если впоследствии появится странность с сохранённой формулой, открытием, рисунком мелом или игрой на сервере.

---

## 1. Зачем понадобился этот patch

До patch логика кнопки получения открытия была такой:

1. клиент собирал формулу на экране;
2. клиент отправлял её JSON и номер текущего открытия;
3. сервер разбирал именно присланную формулу;
4. сервер считал score;
5. если dimensional score был достаточен и не было conflicts, прогресс открывался.

Проблема состояла **не в обычном клиенте**. В штатном интерфейсе target-величина уже стояла в locked slot слева и не была доступна в лотке: обычный игрок не мог собрать `F = F`, просто перетащив вторую `F` из tray.

Проблема была только в изменённом клиенте или ручной отправке пакетов. Такой клиент может создать `SubmitPayload` напрямую и не обязан следовать ограничениям GUI/лотка. Сервер тогда не проверял, что присланная формула действительно выросла из seed-пазла этого мира, поэтому самостоятельное `F = F` служит примером *сетевого forged payload*, а не обычного игрового действия. Аналогично можно было отправить любую другую удобную самосогласованную формулу и получить открытие/предмет, не решая текущую задачу.

Клиентский интерфейс не является границей безопасности в мультиплеере: пользовательский клиент можно изменить. Границей должен быть сервер.

### Что не было целью patch

Patch **не** меняет:

- таблицу quantities, их размерности или значения;
- алгоритм подсчёта dimensional/numeric score;
- порог открытия `90`;
- рецепты, свитки открытий, recipe-book unlocks или advancement chain;
- визуальный рендер меловой доски;
- существующий игровой способ оборачивать узел через умножение или деление;
- Dyson/Black Hole renderer.

## 2. Новая модель: сервер знает исходную задачу

Серверная версия каждой задачи уже существует в `ChalkboardWorldData`. Она строится из world seed и индекса открытия через `GameSolver`.

При сохранении или попытке получить открытие сервер теперь делает следующее:

1. берёт `currentDiscoveryIndex` из server-side attachment игрока;
2. отклоняет переданный клиентом index, если он отличается от текущего;
3. берёт puzzle для этого индекса из `ChalkboardWorldData`;
4. разбирает клиентский JSON только в безопасных границах;
5. сравнивает дерево с серверным исходным skeleton;
6. проверяет, что quantities, поставленные игроком, реально доступны этому игроку;
7. только для Claim запускает обычный `Evaluator` на сервере;
8. выдаёт прогресс, предмет/XP и secret unlocks только после успешной проверки.

Таким образом формула с экрана остаётся вводом игрока, но не становится источником истины.

## 3. Что считается честной формулой

### 3.1. Не требуется sample solution

Patch **не** требует текстового совпадения с `sampleSolution` и не сравнивает строку JSON с каким-либо шаблоном.

Игроку разрешено найти другое физически и численно корректное преобразование. Это важно: формула на доске — не ввод одной заранее угаданной строки.

Пример допустимого направления преобразования:

```text
F · t = (m · a) / Hz
```

Если такая формула была построена стандартными действиями доски, содержит исходные защищённые части текущей задачи и получает server-calculated score не ниже порога, она принимается. В добавленном self-test этот пример даёт score `98`: один штраф за дополнительный узел слева и один за дополнительный узел справа.

### 3.2. Что именно обязано сохраниться

Для текущей server puzzle должны сохраниться:

- корневое равенство;
- его server-generated identity;
- базовые операции исходной схемы;
- все исходные slots;
- их положение в исходной части дерева;
- locked quantities без подмены;
- locked target на левой стороне равенства.

Исходные пустые slots по-прежнему можно заполнять. Добавленные узлы можно создавать вокруг уже имеющегося узла точно так же, как это делает `Manipulate.wrapNode`:

- умножение слева или справа;
- деление сверху или снизу;
- новый slot, помеченный как added.

Добавленную обёртку можно затем убрать штатным действием доски. После удаления исходный skeleton снова совпадает с серверным.

### 3.3. Что намеренно отклоняется

Сервер отклонит следующие варианты:

| Вариант | Почему |
|---|---|
| Отдельное `F = F`, вручную сформированное изменённым клиентом | В нём нет исходного skeleton текущего puzzle. Штатный UI и до patch не выдавал вторую target-величину из лотка. |
| Пересозданная с нуля формула с правильной размерностью | Она не содержит обязательные узлы seed-задачи. |
| Подмена locked `m` на другую величину | Locked slot должен иметь исходный quantity ID. |
| Перенос target на правую сторону | Target должен остаться server-locked частью левой стороны. |
| Добавление target `F` в новый/пустой slot ради тавтологии вручную сформированным payload | Сервер повторяет правило уже существующего UI: target нельзя подставить в управляемый игроком slot. |
| Quantity следующего tier или закрытый secret | Сервер сверяет доступность с progress игрока, а не с UI клиента. |
| Добавленное `+`, `−`, power или bare number | Стандартный интерфейс доски таких added-узлов не создаёт; допустимы только added `×` и `÷`. |
| Дублирующиеся node IDs | Они могут исказить ID-keyed maps evaluator'а, поэтому отвергаются до вычислений. |
| Дерево с отсутствующим child/неизвестным quantity | Оно отвергается до `Evaluator`, а не может вызвать ошибку на сервере. |

Creative-игрок и оператор с permission level 2 по-прежнему имеют тот же режим cheats, который им уже показывал клиент: для их собственных slots разрешены все quantities. Это сознательное сохранение существующего admin/creative поведения.

## 4. Условия Claim после structural check

Когда выражение успешно прошло проверку принадлежности пазлу, сервер использует обычный общий `Evaluator`.

Для Claim одновременно требуются:

1. формула complete — пустых или неизвестных slots нет;
2. нет dimensional conflicts;
3. существует `sFinal`;
4. `sFinal >= Evaluator.DISCOVERY_THRESHOLD` (сейчас `90.0`);
5. `analysis.discovery == true`.

Важно: проверяется **итоговый** score, а не только ранний dimensional score `sD`. Поэтому normal numeric layer, anti-inflation cancellation и штрафы added slots продолжают работать точно так же, как задумано в игре.

Secret quantity discovery теперь запускается только после этого полного успешного Claim. Раньше secret unlock можно было попытаться вызвать произвольной корректной размерностной формулой вне проверки current puzzle.

## 5. Сохранение формулы и рисунка

### 5.1. SaveExpr больше не является обходом проверки

`SaveExprPayload` не открывает награды и не производит score, но теперь он всё равно проверяется. Сервер принимает save только если:

- index равен `currentDiscoveryIndex` на сервере;
- formula JSON безопасно разбирается;
- дерево относится к текущему seed puzzle;
- locked portions не подменены;
- размещённые игроком quantities действительно доступны.

Неполная формула для сохранения разрешена — именно это нужно, чтобы можно было продолжить решать позднее.

Это также закрывает старую возможность заспамить attachment множеством сохранений под произвольными integer indices.

### 5.2. Почему в Sync дополнительно валидируется сохранённая формула

Перед отправкой Sync сервер повторно проверяет сохранённую формулу. Если она невалидна, слишком велика или относится к другой задаче, клиент получает свежий server puzzle вместо потенциально повреждённого JSON.

Это защита от:

- старого повреждённого save;
- вручную отредактированных player data;
- сохранения, оставшегося от другого stage;
- старого клиентского exploit payload.

Рисунок мелом не участвует в выдаче открытия и остаётся отдельной визуальной строкой. Он не должен влиять на формулу или progression.

## 6. Лимиты размера: что это означает на практике

### 6.1. Formula JSON: 32 KiB

Для `exprJson` установлен network/parser limit **32 KiB** (32 768 UTF-8 bytes в packet codec; parser также не принимает строку длиннее этого практического предела).

Это не лимит «32 KiB на всю доску» и не лимит количества открытий. Это лимит одного отправляемого JSON-дерева формулы.

Почему он нужен:

- формула — единственный клиентский JSON, который сервер рекурсивно разбирает и вычисляет;
- без разумной границы изменённый клиент может прислать огромную строку или очень глубокую вложенность;
- размер пакета сам по себе не доказывает, что tree безопасен для evaluator'а.

Почему это не должно затронуть обычную игру:

- обычное discovery tree содержит десятки, а не сотни nodes;
- сериализованные IDs короткие (`cb_...`, `s_...`, `op_...`);
- 32 KiB существенно больше нормальной формулы с несколькими десятками обёрток;
- отдельный structural limit допускает до 192 nodes и глубину до 48, то есть много больше любого seed puzzle.

Практически это значит, что формула сможет содержать исходную puzzle structure и десятки дополнительных умножений/делений. Чтобы упереться в node limit, пришлось бы вручную построить очень длинную цепь из многих десятков added operations — это уже не рабочий сценарий решения открытия, а способ создать экстремальное дерево.

Если когда-либо в будущем геймдизайн осознанно потребует формул крупнее 192 nodes, надо увеличивать **вместе** три значения и проверить производительность:

```java
Serde.MAX_JSON_CHARS
Serde.MAX_TREE_DEPTH
Serde.MAX_TREE_NODES
ChalkboardNetwork.MAX_EXPR_JSON_BYTES
```

Просто поднять один packet limit недостаточно и нежелательно: evaluator всё равно должен получать ограниченное tree.

### 6.2. Drawing JSON: сохранён прежний лимит 256 KiB

Рисунок мелом и freeboard data отправляются в `drawingJson`. Для него после корректировки сохранён прежний предел **256 KiB / 262 144 bytes**, который уже был в проекте до server-authority patch.

Это важно для совместимости: patch не должен сделать обычные крупные рисунки вдвое меньше допустимого прежнего размера.

256 KiB — это заметно больше одной обычной меловой записи. Точное число точек зависит от количества цифр координат и freeboard JSON, но при рисовании без freeboard это ориентировочно многие тысячи точек. Лимит всё ещё существует, чтобы один клиентский пакет не мог бесконтрольно раздувать persistent player data, но для рисунка он не ужесточён относительно прошлой версии.

Если клиент пытается отправить больше, чем позволяет сам packet codec, это не попадает в серверный attachment. Обычный пользователь не должен видеть этого ограничения при нормальном рисовании. Если в будущем появится реальный художественный сценарий, который стабильно превышает 256 KiB, лучше не бесконечно поднимать одну JSON-строку, а ввести сжатый/сегментированный формат strokes.

### 6.3. Ограничения structure, независимые от размера текста

Даже корректный по размеру JSON отклоняется, если он превышает:

| Параметр | Значение | Причина |
|---|---:|---|
| Максимальная глубина expression tree | 48 | Защита рекурсивных обходов. |
| Максимум expression nodes | 192 | Защита CPU/памяти и ID maps. |
| Максимальная длина node ID | 96 символов | Не позволяет использовать ID как большой payload/map key. |
| Повтор node ID | запрещён | `Evaluator` хранит результаты по ID. |
| Неизвестный quantity ID | запрещён | Сервер использует только registry `Quantities`. |
| `NaN` / infinity в numeric fields | запрещены | Защита numeric evaluator'а. |

Эти значения относятся к **формуле**, не к рисунку.

## 7. Стабильность между измерениями и рестартами

### 7.1. Одна world puzzle cache для всех измерений

`ChalkboardWorldData.get(ServerLevel)` теперь всегда использует data storage **overworld**.

Причина: progress игрока один, независимо от того, решает ли он доску в Overworld, Nether, End или пользовательском измерении. До этой правки вызов из разных измерений мог создать разные in-memory caches одной и той же логической задачи. Содержимое задачи генерировалось от одного seed, но generated node IDs могли отличаться.

Теперь один серверный источник puzzle используется везде:

```text
любой ServerLevel → server.overworld() → единый ChalkboardWorldData
```

### 7.2. Стабильные IDs базовых узлов

`Expr.nid(...)` использует process-local счётчик. Такой ID удобен при создании дерева, но сам по себе не стабилен между рестартами сервера.

Поэтому после seed generation `ChalkboardWorldData` пересобирает именно **базовую серверную puzzle** с IDs, которые зависят от:

- индекса stage;
- пути node внутри дерева (`root`, `root_l`, `root_r`, …).

Примерный вид: `cb_0_root`, `cb_0_root_l`, `cb_0_root_r_l`.

Это даёт два полезных свойства:

1. один world seed + один index всегда дают одинаковую identity базового skeleton;
2. сохранённая честная формула, созданная после этого patch, остаётся распознаваемой после перезапуска сервера.

IDs добавленных игроком nodes остаются клиентскими IDs, но они проверяются на формат, уникальность и расположение вокруг базового skeleton.

### 7.3. Поведение старых сохранённых формул

Формулы, записанные **до** появления стабильных baseline IDs, могут иметь runtime-generated IDs старого запуска сервера. Их невозможно надёжно сопоставить с новым server skeleton без ослабления проверки и потенциального принятия поддельной структуры.

Поэтому при первом Sync после обновления такая старая формула может быть заменена на свежую server puzzle. Это затрагивает только текущую незавершённую раскладку формулы, а не:

- уже полученные свитки;
- recipe tier unlocks;
- advancement progress;
- secret quantities;
- рисунок мелом.

После того как формула один раз сохранена версией с этим patch, её базовые IDs стабильны для последующих рестартов.

## 8. Кодовая карта

| Файл | Роль после patch |
|---|---|
| `src/main/java/com/gonzotech/chalkboard/core/ChalkboardSubmissionValidator.java` | Новый чистый server-side structural validator. Не зависит от Minecraft classes, поэтому его легко тестировать. |
| `src/main/java/com/gonzotech/chalkboard/network/ChalkboardNetwork.java` | C2S packet bounds, authoritative Save/Submit flow, Sync fallback для невалидного save. |
| `src/main/java/com/gonzotech/chalkboard/core/Serde.java` | Bounded и complete JSON parse expression trees. |
| `src/main/java/com/gonzotech/chalkboard/core/ChalkboardWorldData.java` | Единый overworld cache и stable baseline node IDs. |
| `src/main/java/com/gonzotech/chalkboard/core/SelfTest.java` | Headless regression scenario для валидного `F·t = m·a/Hz`, вручную сформированного сетевого `F=F`, locked substitution, unavailable quantities и malformed JSON. |
| `src/main/java/com/gonzotech/chalkboard/core/Evaluator.java` | Не менялся: остаётся единственным общим score engine. |
| `src/main/java/com/gonzotech/chalkboard/core/Manipulate.java` | Не менялся: описывает разрешённые клиентские transformations, на которые ориентируется validator. |
| `src/main/java/com/gonzotech/chalkboard/progress/PlayerChalkboardProgress.java` | Не менялся по формату; хранит formulas/drawing/progression per player. |

### Главные публичные точки validator'а

```java
ChalkboardSubmissionValidator.validateDraft(puzzle, expression, quantityPredicate)
ChalkboardSubmissionValidator.validateClaim(puzzle, expression, isInfiniteMode, quantityPredicate)
```

`validateDraft` проверяет структуру и доступность quantities, но разрешает пустые slots.

`validateClaim` сначала выполняет ту же проверку, затем вызывает `Evaluator.analyze(...)` и применяет score/conflict/complete условия.

## 9. Мультиплеерный аудит других custom payloads

В рамках patch были просмотрены все зарегистрированные client-to-server custom payload paths.

### Cesium blast request

`CesiumBlastRequestPayload` несёт только `BlockPos`. Сервер повторно проверяет:

- игрока и текущий `ServerLevel`;
- что по позиции действительно находится `CesiumOreBlock`;
- дистанцию до игрока;
- exposure руды;
- server-side cooldown в `CesiumOreBlock.tryBlast`.

Клиент не может авторитетно вызвать взрыв в произвольной точке.

### Pipe flow HUD requests

`PipeFlowNetwork.RequestPayload` и `ItemFlowRequestPayload` нужны только для HUD гаечного ключа. Сервер проверяет:

- дистанцию не более 8 блоков;
- block state на позиции;
- что block действительно является `PipeCarrier`;
- что он переносит запрошенный тип pipe;
- границы ordinal type ID.

Ответ потока предметов ограничен top-5 items. Клиент не задаёт количество потока и не меняет pipe state.

### Scholar Notes request

`NotesNetwork.NotesRequestPayload` пустой. Сервер читает playtime и recipe-tier из server-side player data и отправляет только ответ для GUI. Client payload не меняет progression.

### Space sky payloads

`SpaceSkyNetwork` в просмотренной регистрации использует S2C payloads. Они не являются client-authoritative каналом изменения мира.

### Вывод аудита

Проверенный custom C2S набор не содержит другого найденного progression/world-state обхода уровня старого Chalkboard Submit. Основной авторитетный дефект был в Chalkboard, и он закрыт этим patch.

## 10. Что проверить вручную после сборки

Ниже нормальный smoke-test без специальных модифицированных клиентов.

### Одиночный мир

1. Создать новый мир.
2. Открыть меловую доску.
3. Поставить доступный quantity в пустой slot.
4. Закрыть и снова открыть доску — формула должна сохраниться.
5. Нарисовать несколько strokes, закрыть/открыть — рисунок должен сохраниться.
6. Решить первую задачу обычным способом.
7. Нажать Claim — должен выдаться привычный discovery item / progression.
8. Активировать свиток — recipes и advancement должны вести себя как раньше.

### Преобразование формулы

1. На подходящей задаче обернуть часть формулы через `×` или `÷`.
2. Убедиться, что added slot заполняется доступным quantity.
3. Убедиться, что готовая эквивалентная формула с итоговым score >= 90 принимается.
4. Удалить added node стандартным действием и снова сохранить.

### Multiplayer

1. Подключить двух игроков к одному dedicated/integrated server.
2. Оба открывают доску: у каждого собственное per-player progress, но server puzzle для одного мира одинакова.
3. Первый игрок сохраняет незавершённую формулу; второй не должен её получить.
4. Первый игрок решает/claim'ит stage; второй остаётся на своём current stage.
5. Переместить первого игрока в другое измерение и снова открыть доску: текущая puzzle не должна поменяться только из-за измерения.
6. Перезапустить сервер, снова открыть доску: формула, сохранённая уже этой версией, должна остаться распознаваемой.

### Headless self-test

В `SelfTest` добавлены проверки:

- сервер принимает честное `F*t = m*a/Hz` с score 98;
- сервер отклоняет независимое `F=F`, если оно вручную прислано изменённым клиентом;
- сервер отклоняет замену locked component;
- сервер отклоняет added quantity без доступа;
- `Serde` отклоняет expression с отсутствующим child.

На рабочей Java/Gradle среде запускать после компиляции по существующей подсказке класса `SelfTest`.

## 11. Если что-то выглядит сломанным

### Симптом: доска открылась с чистой исходной формулой вместо незавершённой старой

Наиболее вероятная причина: эта формула была сохранена старой версией до stable baseline IDs, либо структура/quantity уже не соответствует текущему server puzzle.

Что проверить:

1. не изменялся ли world seed;
2. не изменялся ли вручную `currentDiscoveryIndex` через admin command;
3. сохранена ли формула уже после установки этого patch;
4. нет ли в server log ошибки от другого мода/повреждённого player data.

Прогресс открытий и рисунок при этом не должны сбрасываться.

### Симптом: кнопка Claim видна, но сервер не выдаёт открытие

Кнопка на клиенте всё ещё скрывается/показывается по локальному preview evaluation. Сервер — окончательная проверка. Причины отказа могут быть такими:

- клиент показывает stale formula после получения нового server Sync;
- решается уже не current stage;
- quantity был доступен в клиентском cheats UI, но игрок не creative/op на сервере;
- baseline slot/locked portion не сохранён;
- итоговый score на сервере меньше 90 из-за penalties/numeric layer;
- выражение не прошло structural validation.

Для нормального клиента после Sync нужно заново открыть/синхронизировать экран. Для разработки полезно поставить breakpoint/временный log около `validateClaim(...).reason()`; причина предусмотрена в `ChalkboardSubmissionValidator.Result`.

### Симптом: не сохраняется очень большой рисунок

Предел `drawingJson` сохранён прежний: 256 KiB. Если реальный сценарий регулярно превышает его, сначала сохранить пример JSON и измерить его UTF-8 byte size. Не стоит без измерения поднимать предел до мегабайт: лучше решить, нужно ли сжатие strokes или разделение drawing payload на сегменты.

### Симптом: не сохраняется экстремально длинная формула

Проверить количество/глубину nodes. Новые limits намеренно не позволяют превратить expression в сотни вложенных операций. Для штатной discovery puzzle это не требуется. Если в будущем будет официальная механика для очень больших формул, лимиты надо увеличивать согласованно и добавлять performance/regression test.

## 12. Откат и дальнейшие изменения

Patch изолирован в Chalkboard core/network. Он не меняет asset files и не затрагивает Black Hole/Dyson rendering.

Если потребуется временно диагностировать регрессию, полезно сравнивать следующие места:

```text
ChalkboardNetwork.handleSubmission
ChalkboardNetwork.handleSave
ChalkboardSubmissionValidator
ChalkboardWorldData.get
Serde.fromJson
```

Полный откат server-authority patch снова заставит сервер доверять client-crafted standalone formula (например, вручную отправленному `F=F`, несмотря на то что штатный UI такого не строит). Поэтому предпочтительный путь при будущем баге — исправить конкретное правило validator'а или миграцию старого save, а не отключать весь validator.

При расширении board UI нужно сначала обновить validator. Например, если UI когда-нибудь официально научится добавлять power/add/sub nodes, validator должен явно описывать безопасную structural form этих операций; иначе честный новый UI будет корректно отвергнут сервером как неизвестная трансформация.

## 13. История решений

- Renderer experiments для Dyson tint были ранее откачены отдельным commit и не являются частью этого patch.
- Этот patch сохраняет принцип: клиент предлагает выражение, **сервер решает**, является ли оно текущей задачей и заслуживает ли награды.
- Сложные проверки вынесены из packet handler в отдельный класс не для усложнения игры, а чтобы их можно было сопровождать, тестировать и менять без расползания logic по сети/UI.
