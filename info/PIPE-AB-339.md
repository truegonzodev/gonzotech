# Два прогона труб: 0.3.339 A/B

**Архив пары339. В0.3.340 автор выбрал B базой.** Старые JAR/ZIP сохранены. RUN-A/RUN-B из снимка339 проверяют commit и после обновления checkout намеренно откажутся запускать340под старой меткой. Для повторения именно339 используйте его JAR или отдельную распакованную копию339. Актуальный статус — [CURRENT](../docs/CURRENT-STATE.md#d-pipe2).

Исходный338 сохранён в `pipe-snapshots/338-b1779c93`: source ZIP, исходный JAR и manifest с хешами. Для честного сравнения используйте пару339: **A — поиск338 с новым логгером; B — эксперимент с тем же логгером**. Номер версии у обоих одинаковый, режим зашит в JAR. Это локальные артефакты, не публикация релиза.

## Запуск

1. Для обычного экземпляра Minecraft выберите **один** JAR из `pipe-snapshots/339-AB/A` или `B`. Замените мод в своём экземпляре; одновременно A и B ставить нельзя. Остальные моды, JVM, настройки, дальность, тикрейт и графика одинаковые. JVM overrides `gonzotech.pipe.*` убрать, если ранее задавались.
2. Для запуска из исходников можно открыть `RUN-A.cmd`, затем `RUN-B.cmd` в `pipe-snapshots/339-AB`. Они проверяют commit/чистоту runtime и запускают `runClient` с нужным режимом/профилем. После закрытия клиента копируют свежий `run/logs/latest.log` в `pipe-snapshots/339-AB/logs`; мир не копируют и не заменяют.
3. Перед обоими прогонами используйте **две копии одного исходного сохранения** с одинаковыми буферами/топливом/загрузкой. Простое продолжение мира после A даст B другие условия. Автоматического отката мира нет.
4. Войдите, загрузите то же производство и стойте в той же точке. Первые600 серверных тиков — прогрев, затем минимум2000 измеряемых тиков (при20TPS примерно100 секунд). Не открывайте тяжёлые меню/не меняйте производство только в одном прогоне. Выходите из клиента штатно, чтобы сохранить лог.
5. Отдельной парой можно сравнить одинаковый сценарий разрывов/поршня. Статичный прогон показывает цену обслуживания, но почти не проверяет повторное использование коридоров после изменений. Суммы предметов/ресурсов и HUD проверить в обоих режимах.

Подробный старый pipeDiagnostics желательно оставить **false** в обоих запусках. Агрегатный профиль включён в A/B независимо от него. Строка `[GONZOTECH PIPE-SNAPSHOT]` должна показывать `pipe-II-339-A baseline` или `pipe-II-339-B experimental`, `aggregateProfile=true`. Встроенный `snapshot` идентифицирует режим, manifest дополнительно фиксирует SHA-256 JAR/исходников.

## Что прислать

Два полных лога, какой файл относится к A/B, используемый мир/производство и наблюдения: остановки, потери, HUD, показания времени тика. Для внешнего экземпляра сохраните его `logs/latest.log` после каждого запуска под разными именами, иначе следующий запуск его перезапишет.

Из корня проекта сравнение можно получить так:

```text
python audit/pipe_compare.py путь/A.log путь/B.log --output comparison.md
```

По умолчанию исключаются первые600 тиков и неполные окна. Если в файле несколько сессий, укажите `--session-a UUID --session-b UUID` из строк логгера. Для диагностики начальной загрузки есть `--skip-ticks 0`; её не смешивать с устойчивой работой. Скрипт не выбирает победителя автоматически.

## Что измеряет логгер

Одна `[GONZOTECH PIPE-BENCH]` строка на200 серверных тиков; частичное окно при stop. Счётчики сбрасываются после окна, totalTicks — с начала сессии. Интегрированный сервер запускает новый UUID после повторного открытия мира.

| Поле | Смысл |
|---|---|
| tickSpanMeanUs/P50Us/P95Us/MaxUs | Интервал серверных Pre→Post событий, в микросекундах. Не точный vanilla MSPT: некоторые обработчики могут быть за границами интервала, вывод самой строки после замера. |
| SEARCH_NS | Работа поиска/обновления получателей; часть синхронных вызовов вложена в routing-таймеры. Не складывать с ними как независимые расходы. |
| ITEM_NS/FILTER_NS/RESOURCE_NS | Полное время соответствующих routing-вызовов, включая вложенный поиск. |
| STATE_READS/EXPANDED/RESTARTS | Cache-miss чтения геометрии в сервисе, обработанные позиции, рестарты запросов. Не все чтения мира всем модом. |
| PRECISE_SKIPS/ROUTE_KEEPS | Пропущенные нерелевантные позиционные события / удержания плана при безопасном закрытии ребра. |
| WELD_BUILDS/HITS/STEPS | Построенные записи коридоров / replay-попадания / позиции в replay. Нули допустимы на сетях без подходящих коридоров. |
| NODE_ITEMS | Успешно перемещённые предметы обычными узлами; фильтры не входят. |
| resourceChargeMilli | Списанные ресурсы по каналу, включая потери; не чистый приход получателям. |
| pendingMax, cells, queries, corridors | Максимальная очередь окна и размеры кэшей на момент отчёта. |
| gcCount/gcMs/heapUsedBytes | GC и занятый heap всей JVM; во встроенном сервере включают клиент. Не allocation profiler. |

Среднее нескольких окон взвешивается по тикам. Из оконных p95 невозможно восстановить общий p95: сравнение показывает **максимальный оконный p95**, прямо подписанный. Быстрый тик при упавшей передаче не считается успехом. При насыщенных буферах/отсутствии спроса одинаковый счётчик выдачи тоже сам по себе не доказывает равенство поведения.

## Границы эксперимента

B хранит до3 проверенных коридоров на ячейку-владельца8³ и использует их только при единственном BFS-фронте. Лимит3 ограничивает кэш, не сеть. Коридоры сохраняют физические пути/потери и могут пересекать ячейки. PORT-поиск не сжимается; общий метаграф и произвольное локальное восстановление дерева ещё не реализованы. Точные зависимости могут экономить инвалидации, но расходуют дополнительную память/работу. Ускорение заранее не гарантировано.
