================================================================
ТЕКУЩИЙ STANCE (что уже сделано и как это работает)
================================================================

МОДЕЛЬ ПЕРЕДАЧИ — ПАССИВНАЯ:
- Трубы НЕ хранят, НЕ тикают, НЕ буферят, НИКОГО НЕ ВСАСЫВАЮТ.
- Труба = «вынос слива за пределы блока».
- Машина сама ДОБРОВОЛЬНО сливает свою ВЫХОДНУЮ шкалу (не stored).
- Слив тянется по связной цепи труб того же типа (BFS на лету) и
  телепортируется приёмникам за тот же тик. Без сетей-объектов/SavedData/тикера.
- Раздача РАВНОМЕРНАЯ (железное правило) — Transfer.distributeAmong,
  с честной ротацией неделимого остатка по gameTime.

КЛЮЧЕВЫЕ КЛАССЫ (пакет com.gonzotech.machines.network):
- PipeCarrier   — интерфейс «носитель труб»: carries/opensToward/modeFor.
                  Роутер работает ТОЛЬКО через него (не важно труба/узел/связка).
- PipeBlock     — одиночная труба (RotatedPillarBlock), тип фиксирован (WIRE/HEAT).
                  Тонкий брусок 4x4x16 в СВОЁМ углу сечения (не по центру).
- NodeBlock     — узел: обычный ПОЛНЫЙ КУБ, открыт во все 6 сторон
                  (connectsAllSides=true). Одна плоская текстура на все грани (temp).
- CompositePipeBlock — связка: несколько типов в одном кубе, каждый в своём углу,
                  типы между собой НЕ соединяются. Генерик по PipeType.
- PipeGeometry  — ЕДИНЫЙ источник геометрии: corner(type) + cornerBox(axis,type)
                  + partAt(...). И хитбокс, и наведение берут центр из cornerBox
                  (никаких рассинхронов).
- PipeRouting   — BFS-слив drain(...). Соединения: opensToward обеих граней навстречу.
- FlowTracker   — транзитный учёт фактического потока за тик, РАЗДЕЛЬНО по типу
                  ([тип][сторона]). Без BE/NBT. Сброс на ServerStoppedEvent.
- PipeFlowNetwork — C2S запрос (pos+typeId) / S2C ответ (два конца оси / сумма у узла).
- WrenchHud     — клиент: наводишь ключом на конкретную трубу пучка → тип/режим/поток.
- ModCompositeAccess — держатель ссылок (composite + singles по типу), сборка/разборка.

РАСКЛАДКА УГЛОВ СЕЧЕНИЯ (4 типа = 4 угла, PipeGeometry.corner):
    [ ]E[ ][ ]F[ ]    E = WIRE  (ток)      верх-лево   {2,10}   [есть]
    [ ][ ][ ][ ][ ]    F = FLUID (жидкость) верх-право  {10,10}  [зарезервировано]
    [ ]H[ ][ ]I[ ]    H = HEAT  (тепло)    низ-лево    {2,2}    [есть]
                       I = ITEM  (предметы) низ-право   {10,2}   [зарезервировано]

РЕЖИМЫ (грань труба↔машина): AUTO=вход+выход; PULL(«забор»)=машина→сеть, сеть не отдаёт;
PUSH(«отдача»)=сеть→машина, машина не сливает.

СБОРКА/РАЗБОРКА СВЯЗКИ:
- Ставишь трубу; в руке труба ДРУГОГО типа + ПКМ по стоящей → блок становится связкой.
- Ключ по связке: ТОЛЬКО обычный ПКМ — крутит режим трубы, В КОТОРУЮ ЦЕЛИШЬСЯ (partAt).
- Сломать блок → выпадают отдельные трубы каждого типа (getDrops).
- Shift/Alt+ПКМ НАМЕРЕННО не занят — зарезервирован под будущие ПОВОРОТЫ труб (Шаг 3).

ПСЕВДОМНОГОБЛОК («сосед обязателен») — ТОЛЬКО топка+котёл:
- Boiler требует примыкающую Firebox (Sinks.hasNeighbor) — ОСТАВЛЕНО, НЕ трогать.
- Stirling БОЛЬШЕ НЕ требует примыкающий Boiler — крутится от пара из буфера,
  откуда бы пар ни пришёл (труба дотянет).
- ElectricFurnace БОЛЬШЕ НЕ требует примыкающий Stirling — плавит от GTU из буфера,
  откуда бы энергия ни пришла (провод дотянет).
- Это чисто ЛОГИЧЕСКОЕ правило в тике (не про энергию): убраны gate-проверки chain.

ОБ ОСИ: пока у связки ОБЩАЯ ось на весь блок (Шаг 1). Попарные независимые
направления — Шаг 2 (см. план).

================================================================
БАГИ, КОТОРЫЕ УЖЕ ПОФИКШЕНЫ (чтобы не ловить повторно)
================================================================
- Вертикаль (axis=Y): блокстейт крутит модель x:90 => MC rotateYXZ(-y,-x,0),
  поэтому Z угла ЗЕРКАЛИТСЯ: cornerBox(Y) = box(u,0,12-v, u+4,16,16-v).
  Из-за неверного знака раньше: вертикальные трубы менялись местами и хитбокс
  одиночной трубы уезжал на место соседа. partAt теперь берёт центр из cornerBox.
- BuiltInRegistries.ITEM.get() в 1.21.4 возвращает Optional<Reference<>> — брать getValue().
- PipeBlock.codec() ДОЛЖЕН быть public (RotatedPillarBlock.codec() public).

================================================================
ИЗВЕСТНЫЕ МЕЛОЧИ (пока НЕ критично, отложено осознанно)
================================================================
- При постановке одиночной трубы «вверх» позиция угла зависит от того, откуда
  смотришь (ось Y корректна, но левый/правый угол не выбирается). Забить пока.

================================================================
ПЛАН (следующие фазы, каждая — ОТДЕЛЬНЫЙ заход/коммит, НЕ сейчас)
================================================================
1) Водные (жидкостные) трубы: PipeType.FLUID + Sink/Source у машин + ассеты.
   Угол {10,10} уже зарезервирован — включатся в связку автоматически.
2) Предметные трубы: PipeType.ITEM (+ инвентарная передача). Угол {10,2}.
3) 4-стаканый пучок целиком + ПОВОРОТЫ парами как «кубик рубика 2x2»:
   - per-type ось вместо общей (Шаг 2);
   - правило непересечения: два типа могут идти по разным осям, только если
     разнесены по третьей оси (верх/низ или лево/право);
   - multipart-модели под per-type ось;
   - UX конфигурации поворота ключом (ЛКМ / Shift+ПКМ — продумать).
4) (Позже) блок-крышка внутри пучка («спрятать провода под любой блок») —
   ТРЕБУЕТ BlockEntity (произвольный блок в блокстейте не хранится) + рендер.

================================================================
ЖЕЛЕЗНЫЕ ПРАВИЛА (не нарушать)
================================================================
- Распределение РАВНОМЕРНОЕ, не приоритетное (навсегда).
