## Задачи и состояния

Постоянный ID (например DOC-001, D-R1, D-З11) сохраняется при переносе. Заголовок задачи в CURRENT/DEFFERED — `### ID — название`. Состояния: в процессе; заблокировано; реализовано, ждёт проверки; закрыто; отложено; отменено/заменено. Кодовая реализация не равна игровому закрытию.

Закрытая в версии `0.3.N` задача остаётся в CURRENT четыре последующих patch-версии; убрать при достижении `0.3.(N+4)`. Пример: закрыто 311 → убрать в 315. Это не четыре коммита и не четыре документационных правки. Удаление записи обязательно логируется в HISTORY. Дат закрытия не выдумывать; старые завершённые работы не импортируются в CURRENT как новые активные задачи.

При переносе в DEFFERED активный заголовок убирается из CURRENT; недавняя строка «перенесено, ID/ссылка» допустима как статус, не копия задания. Списки активных ID не пересекаются. При отмене/замене сохраняются основание и преемник в HISTORY; не оставлять отменённое как открытый пункт.

## История и доказательства

HISTORY — факт событий по версии, включая создание/закрытие/удаление записей CURRENT и изменения документов. Несколько docs-only шагов могут быть под одной runtime-версией, с датой/коммитом; не повышать mod_version ради счётчика. Исторические фразы сохраняются с версией и не являются нынешним контрактом.

Тематический файл содержит действующую спецификацию и собственную версионную историю значимых изменений со ссылками в HISTORY, а не копию общего журнала. Утверждение автора, предложение ассистента, реализованный код и игровой результат отмечаются раздельно.

Если версия первого упоминания не установлена, писать «не установлена; самое раннее найденное свидетельство…». Не приписывать позднему коммиту дату первоначального замысла. Не дополнять историю вымышленным содержимым ради полноты.

## Обязательный пайплайн каждого шага

1. **Сверить базу.** Проверить ветку, рабочие изменения, актуальный авторский коммит и runtime-версию; чужой WIP не присваивать. Прочитать RULES → DOCS_RULES → CURRENT-STATE → все профили затронутой системы. README не рабочая память.
2. **Разобрать связи до реализации.** Определить затрагиваемые BE/буферы/переносы, UI/JEI, гейты, сеть/сохранение, геометрию/генерацию и внешние моды. Выбрать владельцев фактов по таблице ниже, а не создать один новый «итоговый» документ.
3. **Сверить реальность и спросить.** Код, авторское решение, документы и архив — отдельные источники. Всё даже мельчайше непонятное спросить у автора; противоречие прямо процитировать/показать в чате и спросить, где правда. Не исправлять неизвестное предположением и не расширять заявку. Пока ответ не получен, затронутое решение заблокировано, а не «как будто согласовано».
4. **Отметить задачу.** Завести/обновить постоянный ID и статус в CURRENT. Перенос из DEFFERED сохраняет ID; не делать две активные копии. Концепт/замысел сам не становится задачей. Вопрос/блокер указать конкретно.
5. **Сделать согласованное и сразу синхронизировать профили.** При каждом изменённом контракте писать актуальный результат в соответствующий тематический файл: методы/буферы/слоты/лимиты, форма/порты, страницы/гейты, зависимости и ограничения. Избирательно **дублировать** значимый факт там, где он нужен читателю другой системы; ссылки дополняют, но не заменяют обязательное описание. Если профиль говорит старое, шаг не закончен.
6. **Собрать полную хронику в HISTORY.** Версия/база, запрос и ответ автора, создание/смена статуса/перенос/закрытие/удаление задачи, изменения кода **и документации**, проверки и их пределы. «Куча» полного лога допустима здесь; в остальных документах только их собственный актуальный контракт и существенная тематическая история. Не копировать весь HISTORY в профили.
7. **Сверить состояние и последствия.** CURRENT — только текущий статус/блокеры и недавнее закрытое (четыре патча), не хронология. DEFFERED — только конкретное отложенное открытое; отменённое/заменённое вывести из открытой очереди с основанием в HISTORY. Новая информация не должна оставаться только в сообщении чата.
8. **Проверить документационную связность.** Переименование: обновить навигацию, живые ссылки, audit-проекции и маршруты migration metadata, не менять байты замороженных оригиналов. Проверить таблицы против кода, `python3 audit/docs_structure_test.py`, `python3 audit/doc_links.py`, `git diff --check`; выполнить релевантные code/resource tests. Результаты и SKIP/FAIL занести в AUDIT и HISTORY; не выдавать source-пин за игру.
9. **Финальный проход перед доставкой.** Просмотреть изменённые кодовые файлы и убедиться, что каждый изменённый контракт отражён во всех связанных профилях. Обновить CURRENT и короткую тематическую историю в тех же изменениях, а не обещать «допишем позже». Коммит/пуш, сообщить автору результат и **каждую** оставшуюся несостыковку/вопрос. Runtime-версию не повышать ради docs-only работы.

### Матрица связанных документов: где избирательно дублировать факт

| Что изменилось | Где обязательно сверить и обновить затронутое |
|---|---|
| BE, capacity, receive*, перенос, производство | MACHINES; CAPABILITIES при I/O/сети; MULTIBLOCK при портах/форме; JEI при display; SUPER_CRUCIAL_FILE при геометрии GUI; PROGRESSION при доступности |
| Сборка/распад/чанки/контроллер структуры | MULTIBLOCK; MACHINES для ресурсов/цикла; REACTORS для реактора; CLEANROOM для условий литографа; CAPABILITIES для routing; JEI/заметки для затронутого показа |
| Формулы доски, подсказки, награды | CHALKBOARD; PROGRESSION для активации/tiers; PSYCHE для источников clue/эффектов; SCHOLAR_NOTES только если меняются её флаги/страницы |
| Страницы, гейты заметок, избранное | SCHOLAR_NOTES; PROGRESSION для смыслов открытия; тематический файл описываемой механики; DEFFERED для реально закрытого/перенесённого пункта |
| Внешний мод / dependency / bridge | INTEGRATIONS; build/metadata если изменение действительно кодовое; JEI/CAPABILITIES/WORLDGEN/AUDIO_VISUAL по области; не менять зависимость ради исправления одной формулировки |
| Биомы / features / biome source | WORLDGEN и INTEGRATIONS; заметки при изменении описанной генерации; RAD_WORLD только при реально затронутом контракте, без самовольной правки runtime |
| Небо, fog, жидкости, shader compatibility | AUDIO_VISUAL и INTEGRATIONS; профиль механики при затронутом эффекте; не смешивать визуал с балансом/дозой |
| Решение автора / новый концепт / правило | RULES или AUTHORS-NOTES/концепт по уровню обязательства; профиль, CURRENT/DEFFERED только при реальной задаче; происхождение в HISTORY |
| Тесты, запуск, уровень доказательства | AUDIT; HISTORY целиком; профиль кратко о релевантной проверке/ограничении; CURRENT о статусе |

Во **всех** строках дополнительно обязательны актуальный CURRENT-STATE и запись в HISTORY. Обновляются именно затронутые контракты; не размножать весь текст по всем файлам и не писать «всё остальное в истории» вместо тематической спецификации.

### Усиленная сверка после миграции

По правилу №24 автора до **0.3.361** включительно (50 последующих патчей после фактической миграции на **0.3.311**) искать обрывки, старые решения и расхождения **также в docs/archive** по каждой затронутой теме. Это временное обязательное исключение к обычному чтению архива «по необходимости». Старый текст не становится заданием автоматически. Каждое расхождение явно показывать автору в чате и спрашивать, где правда. После 0.3.361 правило можно убрать отдельным зафиксированным решением; исходники архива не переписывать.

Исходные **75 файлов** перенесены побайтно в [legacy-архив](archive/README.md), включая прежний архив, логи и таблицы. `manifest.json` хранит SHA-256 и маршруты переноса; `sections.json` — 4173 заголовка/пункта без автоматической постановки в очередь. [Карта семантических решений](archive/legacy-0.3.311/MIGRATION-MAP.md). Замороженные тексты не переписываются; новые выводы пишутся в живые файлы.
