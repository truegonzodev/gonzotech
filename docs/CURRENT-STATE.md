**Кандидат лечения:** стабильная идентичность физических владельцев (обе половины/позиции/сущность), повторное разрешение живого контейнера при commit; не сравнивать только координату, чтобы не принять заменённый BE. Проверить новый wrapper того же сундука, разделение/замену половины, обычный BE и вагонетку. Взаимосвязь с14; метод ещё не применён.

#### 2. Одноштучные карты Плотника и автоматизация

#### 3. Усечённый BFS и большие сети

**Источник:** авторская проба budget2→visited3; source: sentinel2 затирается `visitedOut[0]=visited.size()`. Частичный результат может попасть в полный кэш; число2 также конфликтует с настоящим количеством посещений.
**Выбранное направление автора:** отдельно complete/visited/result; для действительно больших сетей продолжение между тиками. Уточнить структуру per-level очереди/справедливость; сохранять frontier, но сбрасывать при изменении топологии/выгрузке. Регрессии budget1/2/граница/несколько стартов/большая сеть: дальние sinks в итоге находятся, частичный результат не считается полным. Начинать заново каждый тик недостаточно.

#### 4. Подъехавшая контейнер-сущность

**Реализовано в322, ждёт игровой приёмки/разрешения на архив.** В ItemRouting.sinksCached заменено `version equal OR age≤TTL` на **оба условия одновременно**. Пустой результат больше не живёт бесконечно при неизменных блоках. TTL40 и BFS budget2048 не менялись; при изменении версии поиск обновляется и внутри TTL. Existing liveSinks/sinkLive перед передачей сохранены, отказ/исчезновение приёмника по-прежнему не разрешают использовать старую цель.
**Проверки:**126assertions исполняют production cache methods,5/5 мутаций отвергнуты, включая точное возвращение старогоOR. Весь ItemRouting входит в прежний typecheck. MC lookup/BFS discovery здесь doubles, не серверная проба вагонетки/переноса.
**Граница:** при исчерпанном BFS-бюджете прежний fallback может отложить пересчёт до появления бюджета; это не решение справедливости/продолжения большой сети3. Не обещать фиксированный срок при насыщенной сети. В небольшой загруженной сети с доступным бюджетом — обновление после существующих40тиков (граница age40ещё hit, age41пересчёт).

#### 5. Ограниченная загрузка чанков предметными трубами

**Уточнение автора:** загруженная труба может загрузить **непосредственно соседний чанк источника/приёмника через границу чанков** (пример: сундук1,1 / труба1,2). Это не загрузка удалённых endpoints всей сети; фильтр/сепаратор не endpoints, линия сама по себе инертна и не вызывает цепь прогрузки.
**Состояние:** метод ещё не применён. Нужны bounded adjacent lookup/подтверждение endpoint и lifecycle загрузки; проверка неизвестного unloaded соседа не должна разрешить BFS или тикающим транзитным трубам рекурсивно грузить следующий чанк. Исследовать сохранённое подтверждение соседнего endpoint vs безопасную ограниченную пробу, не обещать определить неизвестный блок без чтения/метаданных. Обязательны instrumented load-count tests на границе, пустом/трубном соседе, filter/separator и километровой линии. Прогрев Плотника5×5 не расширяется.

#### 6. Дорогие кнопки и begin/end Fence

**Source:** у payload нет rate gate, тяжёлые кнопки синхронно сканируют; Fence.begin до ACK может повторно создавать Session со stack.copy.
**Автор выбрал:** один активный тяжёлый job на BE; одинаковые повторы объединять, конфликтующие запросы отклонять; Stop приоритетен; кэшировать результаты. После **завершения** — тихий cooldown10сек **отдельно для каждого типа задачи** (TNT не включает scan cooldown). Пакетные лимиты/размер порции ещё подобрать и проверить отдельно. Ключ кэша должен учитывать изменившийся мир/материалы; cached operation не может повторно тратить/выдавать ресурсы или забыть важное изменение мира.
**Метод ещё не применён:** state machine job/operation-scoped cooldown, дедуп/cache без старых side effects; end/close/stop/disconnect не теряются. Fence требует отдельной menu/sequence-state, допустимый end/ACK не отбрасывается из-за begin-бюджета. Пробы: spam/reordered/duplicates,2игрока к одномуBE, вложенный inventory, completion→cooldown→new run, независимость TNT/scan, сохранение сумм/дозы. Радиационная формула не меняется.
