# Критические баги, дюпы и потери

База: 0.3.332 / bc1da5bc. [Карта пакетов](<00 — Карта пакетов.md>). Приоритет исполнения после выбора автором: P1.

Пакет для повреждения состояния и утраты ресурсов. В текущем аудите подтверждены потеря ТВЭЛа и создание/стирание наведёнки. Новый дюп количества предметов и новый краш не установлены. Старый CRASH-001 с внешней причиной не переоткрывать.

## CRIT-1 — устаревшее меню реактора теряет ТВЭЛ

Источник: A1. Доказательство: нативный серверный GameTest с реальным menu.clicked, не ручная игра автора.

Код: [ReactorFuelInventory](../src/main/java/com/gonzotech/machines/reactor/ReactorFuelInventory.java), [ReactorMenu](../src/main/java/com/gonzotech/machines/menu/ReactorMenu.java).

Инвентарь меню захватывает список чехлов. stillValid/canMutate проверяют сформированность панели и прежнее число слотов, но не действующую принадлежность захваченных BE структуре. Совпадение координат/вместимости не доказывает совпадение физического владельца.

Воспроизведение на серверном стенде:
1. Сформировать реактор 4×4×4 с пустым чехлом; открыть меню игроком рядом с панелью.
2. В одном тике удалить чехол, поставить новый и восстановить структуру с прежней вместимостью до закрытия меню.
3. Проверить старое stillValid: возвращает true. Поместить один UF_TVEL на курсор и выполнить PICKUP в слот 0.
4. Получено: removed(oldSheath)=true; oldFuel=1; liveFuel=0; cursor=0.

Обычное медленное разрушение может успеть закрыть меню; это ограничение воспроизведения необходимо сохранять в отчёте.

Исправление: привязать меню к поколению структуры и/или проверяемому набору действующих владельцев; отвергать устаревшее действие до расходования курсора. Не перенаправлять старое меню молча на новый чехол по той же координате. Просто return из setItem после расходования исходной стопки не является исправлением.

Приёмка:
- Сценарий выше сохраняет единственный ТВЭЛ у игрока/в действующем владельце либо корректно закрывает меню без потери.
- Извлечение, shift-click, drag и cursor при смене структуры не пишут в удалённый BE и не выдают старые ресурсы повторно.
- Два зрителя; смена панели; та же/иная вместимость; unload/reload; быстрое разрушение/пересборка.
- Проверить суммы и сохранность после сохранения/загрузки; не менять реакторный принцип самостоятельного существования чехлов ради интерфейсной защиты.

## CRIT-2 — SidedInvWrapper неправильно объединяет наведёнку

Источник: A2. Доказательство: настоящий NeoForge SidedInvWrapper и применённые mixin в GameTest.

Код: [InvWrapperRadiationMixin](../src/main/java/com/gonzotech/mixin/InvWrapperRadiationMixin.java), [SidedInvWrapperSlotCapacityMixin](../src/main/java/com/gonzotech/mixin/SidedInvWrapperSlotCapacityMixin.java). SidedInvWrapper имеет отдельную реализацию insertItem; хук обычного InvWrapper её не покрывает. Ограничение вместимости отдельным mixin не обеспечивает перенос радиационных данных.

Воспроизведение через side-aware handler Плотника: 4 предмета по 6 mZt/s + 4 по 2 mZt/s должны дать 8 предметов с суммарной эмиссией 32 mZt/s. Вставка через SidedInvWrapper даёт 16, обратное направление — 48. Количество всегда 8. Контрольный обычный InvWrapper сохраняет 32. Это дюп/стирание наведёнки, а не предметов. Обычная воронка и собственная ItemRouting этим тестом неисправными не объявлены.

Исправление: покрыть отдельный путь side-aware insert атомарным переносом sidecar-данных по фактически принятому количеству. Использовать действующий движок, не возвращать динамические NBT/components, паузы или срезание count. Избежать двойного применения при внешней транзакции переноса.

Приёмка:
- Оба направления 4×6 + 4×2 дают 32 mZt/s; итоговая per-item величина 4 mZt/s.
- Пустой слот; частичный приём; переполненный слот; остаток; разные предметы/компоненты; запрет грани; simulate не меняет состояние.
- Сумма наведёнки до/после сохраняется для операции переноса без тика физического распада/облучения; природная эмиссия остаётся свойством типа предмета.
- Количество, cursor и остаток не теряются/не растут; повторить после сохранения/загрузки владельцев.
- Проверить обычный InvWrapper, воронку и трубы как соседние регрессии, не переписывая их рабочие пути без причины.

## Общая доставка

Сначала превратить тесты-наблюдения в отрицательные регрессии: на исходной версии они должны ловить нарушение инварианта, на исправленной — проходить. Не называть зелёный defect-observation тест доказательством лечения. После GameTest нужна отдельная приёмка игровых сценариев автором.

Точечные исправления достаточны; оснований переделывать весь реактор или радиационный движок здесь нет. При реализации синхронизировать REACTORS/MULTIBLOCK/MACHINES для CRIT-1, RAD_ITEMS/CAPABILITIES/MACHINES для CRIT-2 и CURRENT/HISTORY/AUDIT. Миграция старых сохранений и расширение вложенных контейнеров вне пакета.
