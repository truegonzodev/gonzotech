# Тяжёлая дверь 2×2: как устроены составные блоки и что делать нам

**Дата:** 22.09.2026 · **Статус:** разбор по исходникам + проектное предложение (код двери ещё не писан).
**Запрос автора:** «Изучить эту тему тщательно» — как работают составные блоки (дверь = два блока,
хитро связанные в коде), сколько моделей нужно (4 × 1×1×1 или 2 × 1×2), наша дверь будет **2×2,
раздвижная, два состояния, без поворота**.

Разбор сделан по исходникам Minecraft 1.21.4 (Mojang-маппинги, `DoorBlock.java`, `BlockSetType.java`,
`BlockBehaviour$BlockStateBase`), по ассетам ванилы (blockstates/models дверей) и по нашей кодовой
базе (мультиблоки парогенератора и турбины).

---

## 0. Короткие выводы

1. **«Модели 1×2» не существует как сущности.** Модель блока живёт внутри **одной** клетки 16³;
   всё, что выходит за границы, рисуется с поломанным отсечением граней, светом/AO, партиклами и
   анимацией ломания. Поэтому любая конструкция высотой 2 блока — это **минимум два файла моделей**
   (низ и верх), даже если визуально они «одна панель».
2. **Минимум — 4 модели:** низ закрытый, низ открытый, верх закрытый, верх открытый. Ровно то,
   что ты и предположил. **8 моделей** понадобится, только если левая и правая створки должны
   выглядеть по-разному (ванила делает 8 именно поэтому: `..._bottom_left` / `..._bottom_right` —
   в модели нельзя «отзеркалить» UV, только повернуть).
3. **2×2 — это 4 блока**, а не два: один предмет ставит сразу 4 клетки (как ванильная дверь ставит
   верхнюю половину в `setPlacedBy`).
4. **`DoorBlock` наследовать не нужно** (и вредно): он тащит `HINGE` (петли), поворот открытой
   створки на 90°, требование опоры снизу и `BlockSetType`. У нас раздвижная дверь — свой класс
   с состояниями `facing / open / powered / half`.
5. **`BlockSetType` нам не нужен вовсе.** Он существует ради «семейства» (звуки, открывание рукой,
   кнопки/плиты/калитки). Наш блок — не наследник `DoorBlock`, значит берём `SoundType` и звуки
   напрямую. (К слову, в ваниле `BlockSetType.register(...)` **приватный**, так что чужая дверь
   без патча лоадера и не смогла бы завести свой тип.)
6. **Твой пункт 2 уже учтён в контуре:** дверь теперь **замыкает полость, но в расчёте среднего не
   участвует** (Containment 2.0, коммит этого дня). Тег `gonzotech:contour_seal` создан и пуст —
   туда попадёт наша дверь (подробности в §5).

## 1. Как устроена ванильная дверь (по исходникам)

### 1.1 Два блока и пять состояний

```java
public class DoorBlock extends Block {
    public static final DirectionProperty FACING = HorizontalDirectionalBlock.FACING;
    public static final BooleanProperty OPEN = BlockStateProperties.OPEN;
    public static final EnumProperty<DoorHingeSide> HINGE = BlockStateProperties.DOOR_HINGE;
    public static final BooleanProperty POWERED = BlockStateProperties.POWERED;
    public static final EnumProperty<DoubleBlockHalf> HALF = BlockStateProperties.DOUBLE_BLOCK_HALF;
    protected static final float AABB_DOOR_THICKNESS = 3.0F;   // 3 пикселя
}
```
Состояний пять: `facing` (4), `open` (2), `hinge` (left/right), `powered` (2), `half` (lower/upper) —
итого 64 комбинации на блок. Коллизия — **3/16 толщины** (четыре `VoxelShape`: по одному на
сторону света), при открытии форма переезжает на боковую грань (створка «уходит» в соседнюю клетку).

### 1.2 Как две половины находят друг друга

Это и есть то «хитрое связывание»:

| где | что делает |
|---|---|
| `getStateForPlacement` | возвращает **нижний** блок (`HALF=LOWER`) с `facing`, `hinge`, `powered`, `open`; проверяет, что сверху можно ставить (`canBeReplaced`) |
| `setPlacedBy` | ставит **верхний**: `level.setBlock(pos.above(), state.setValue(HALF, UPPER), 3)` |
| `getHinge` | смотрит четыре соседних блока по бокам и считает сумму «полных коллизий» — от неё зависит сторона петель (и то, как две двери рядом образуют двустворчатую) |
| `updateShape` | если сосед по вертикали — тоже `DoorBlock` с **противоположным** `HALF`, то состояние **зеркалится** (`setValue(HALF, doubleblockhalf)` — то есть верх автоматически повторяет `open/facing/hinge` низа); иначе возвращается **AIR** — вторая половина исчезает |
| `canSurvive` | низ: под ним должна быть прочная опора (`isFaceSturdy(..., UP)`); верх: снизу должен быть **тот же самый блок** (`blockstate.is(this)`) |
| `playerWillDestroy` | `DoublePlantBlock.preventDropFromBottomPart(...)` — дроп только с одной половины, иначе дверь падала бы двумя предметами |
| `neighborChanged` | редстоун читается **у себя И у второй половины**: `hasNeighborSignal(pos) \|\| hasNeighborSignal(pos.above()/below())` → ставит `POWERED` и `OPEN`, играет звук |
| `useWithoutItem` | только если `type.canOpenByHand()`; железная дверь рукой не открывается |
| `isPathfindable` | `LAND, AIR → OPEN` (мобы идут только в открытую), `WATER → false` |
| `getShape` | форма зависит от `facing` + `open` + `hinge` (закрытая — поперёк, открытая — вдоль) |
| `playSound` | звуки берутся из `BlockSetType` (`doorOpen`/`doorClose`) |

**Главная мысль:** связь между двумя блоками — это **не ссылка и не BlockEntity**, а **соглашение об
адресе**: сосед по вертикали с противоположным `HALF`. Всю синхронизацию делает `updateShape`
(он вызывается при любом изменении соседа). Именно поэтому ванильная дверь дёшева: у неё нет ни
одного блока сущности.

### 1.3 `BlockSetType` — что это и почему нам не нужен

```java
public record BlockSetType(String name, boolean canOpenByHand, boolean canOpenByWindCharge,
                           boolean canButtonBeActivatedByArrows, PressurePlateSensitivity pressurePlateSensitivity,
                           SoundType soundType, SoundEvent doorClose, SoundEvent doorOpen, ...) {
    public static final Codec<BlockSetType> CODEC = Codec.stringResolver(BlockSetType::name, TYPES::get);
    private static BlockSetType register(BlockSetType type) { TYPES.put(type.name, type); return type; }
}
```
Тип — это «порода дерева/металла» для целого семейства блоков: двери, люки, кнопки, плиты, калитки.
Регистрация в ваниле **приватная** (`private static BlockSetType register`), плюс `CODEC` резолвит
тип по имени из статической мапы — то есть свой тип «на стороне» без патча лоадера не заведёшь.
Для нашего блока (не наследника `DoorBlock`) это не нужно: звук — параметр `Properties.sound(...)`,
открывание — наша логика, кнопки/плиты к двери отношения не имеют.

## 2. Модели и блокстейт: сколько файлов реально нужно

### 2.1 Что говорит ванила

Для **одной** двери ванила держит **8 моделей** и один блокстейт на 64 комбинации:

```
models/block/oak_door_bottom_left.json   models/block/oak_door_bottom_left_open.json
models/block/oak_door_bottom_right.json  models/block/oak_door_bottom_right_open.json
models/block/oak_door_top_left.json      models/block/oak_door_top_left_open.json
models/block/oak_door_top_right.json     models/block/oak_door_top_right_open.json
blockstates/oak_door.json:
  "facing=north,half=lower,hinge=left,open=false": { "model": "...oak_door_bottom_left", "y": 270 }
  "facing=north,half=lower,hinge=left,open=true":  { "model": "...oak_door_bottom_left_open" }
  ...
```
Каждая модель — **одна панель 3 px толщиной внутри своей клетки**:

```json
{ "ambientocclusion": false,
  "textures": { "particle": "#bottom" },
  "elements": [ { "from": [0,0,0], "to": [3,16,16], "faces": {
      "north": { "uv": [3,0,0,16], "texture": "#bottom", "cullface": "north" },
      "east":  { "uv": [16,0,0,16], "texture": "#bottom" }, ... } } ] }
```
То есть: одинаковая геометрия, отличаются **текстура** (низ/верх), **UV** (левая/правая створка) и
положение при открытии. Предмет двери — **плоский спрайт** (`item/generated` + `item/oak_door.png`),
никакой 3D-модели у предмета нет.

### 2.2 Почему «модель 1×2» не вариант

* Модель блока привязана к своей клетке: `from/to` задаются в её 16³.
* Технически можно написать элементы **за** границы (например, `to: [16, 32, 3]` — панель на два
  блока вверх), и это даже отрисуется. Но: `cullface` перестаёт работать правильно (грань не
  отсекается соседом), свет и AO считаются по форме блока (не по модели), партиклы ломания и
  «призрак» блока в хитбоксе будут врать, а при выходе блока за чанк-секцию возможны артефакты.
  Для механики (коллизия, дропы, состояния) верхняя часть всё равно должна быть **отдельным
  блоком** — значит и модель у неё своя.
* Вывод: панель на 2 блока в высоту — это **всегда минимум 2 файла** моделей. Экономия «2 вместо 4»
  невозможна; экономия бывает только «4 вместо 8» (за счёт симметричной текстуры).

### 2.3 Сколько моделей нужно нашей двери — по геометрии

Обе схемы — «раздвижные» (створки уезжают, поворота нет), но рисунок разный:

| схема | как выглядит | модели | текстуры |
|---|---|---|---|
| **A. Раздвиг по высоте** (нижняя половина уезжает в пол, верхняя — в потолок; проход открывается «по середине») | в закрытом состоянии 2×2 — цельная плита; в открытом между половинами щель | **4**: `bottom_closed`, `bottom_open`, `top_closed`, `top_open` | 1–2 (низ/верх) |
| **B. Раздвиг по ширине** (левая створка 1×2 уезжает влево, правая 1×2 — вправо) | в закрытом 2×2 плита; в открытом щель по центру | **4**, если текстура симметрична (левая и правая створки используют одни и те же модели); **8**, если створки разные (как у ванилы) | 1–2 |
| C. С «карманами» (створки видны убранными в стене) | самое «инженерное» | +2 блока «карман» со своими моделями (по 1 на состояние или просто 1 модель) | +1 |

Моё предложение: **схема A, 4 модели, 2 текстуры** (наружная плита + внутренняя/рёбра), потому что
она даёт «проход по середине» без карманов и без зеркалирования UV — то есть самый дешёвый путь к
красивой раздвижной двери. Схема B — если хочется именно «створки в стороны».

## 3. Предлагаемая архитектура нашей двери (4 блока, без BlockEntity)

```
состояния блока:  FACING (север/восток/юг/запад)  OPEN (bool)  POWERED (bool)  HALF (lower/upper)
коллизия:         закрытая = полная плита 16×16×3 (у схемы A — 16×16×8, половина толщины);
                  открытая  = пусто (проход)
прочность:        как у тяжёлого корпуса (бронебетон у нас 12/14, армированный 20/24 —
                  предлагаю 50 / 1200: дверь не должна выноситься крипом)
```

**Как четыре блока узнают друг о друге (без индексов и BlockEntity):**
1. Анкер группы — **нижняя клетка с меньшей координатой** вдоль оси двери (ось = `facing.getClockWise()`).
2. `anchorOf(level, pos)` проверяет до четырёх кандидатов (`pos`, `pos - axis`, `pos - UP`,
   `pos - UP - axis`) и валидирует, что все 4 клетки — наш блок с одинаковыми `FACING`.
   Дешёво: 4 проверки состояний, без поиска.
3. `useWithoutItem` / `neighborChanged` на любой клетке переключают **все четыре** (`setValue(OPEN, ...)`
   всем, `POWERED` тоже синхронизируем — иначе редстоун «залипнет» на одной клетке).
4. `playerWillDestroy`: если клетка не анкер — дроп не выдаём (как `preventDropFromBottomPart`),
   затем удаляем остальные три клетки без дропа. Ставится — одним предметом (в `setPlacedBy`
   или `getStateForPlacement` + установка трёх соседних, как ваниль ставит верхнюю половину).
5. `isPathfindable(LAND/AIR) → OPEN`: мобы ходят только в открытую; закрытая — глухая стена.
6. Открывание рукой: **решаем** (см. вопросы). Варианты: только редстоун (как железная дверь) или
   рукой с задержкой/скрипом.

**Что даёт такая схема:** ноль блок-сущностей, ноль сетевого кода, ноль JSON-структур; дверь
ломается/ставится как обычный блок, синхронизация — через `updateShape`/`neighborChanged`.

## 4. Ассеты: точный список файлов (Blockbench → ресурспак)

| файл | что это |
|---|---|
| `textures/block/third/heavy_door.png` (и, если нужен, `heavy_door_upper.png`) | 16×16, «наружная» плита. Для схемы A достаточно **одной** текстуры: у нижней и верхней модели разные UV, а не разные текстуры |
| `models/block/third/heavy_door_bottom.json` | элемент(ы) панели в закрытом состоянии, `ambientocclusion: false`, `cullface` по внешним граням, `particle` → текстура |
| `models/block/third/heavy_door_bottom_open.json` | та же панель, «уехавшая вниз» (или, для схемы B, сдвинутая вбок) |
| `models/block/third/heavy_door_top.json` / `..._top_open.json` | верхние половины (модель **обязательна** даже если выглядит так же) |
| `blockstates/third_heavy_door.json` | маппинг `facing × half × open` → модель + `y` |
| `items/third_heavy_door.json` + `models/item/third_heavy_door.json` + `textures/item/third_heavy_door.png` | предмет: плоский спрайт (`minecraft:item/generated`), как у ванильной двери |
| `lang/ru_ru.json`, `lang/en_us.json` | `block.gonzotech.third_heavy_door` = «Тяжёлая дверь» |
| `data/gonzotech/tags/block/contour_seal.json` | **добавить** `gonzotech:third_heavy_door` (см. §5) |
| рецепт + (по желанию) страница заметок | «как собрать буфер из двух дверей» |

Пример блокстейта (схема A, 4 состояния × 4 стороны = 16 строк; фрагмент):

```json
{
  "variants": {
    "facing=north,half=lower,open=false": { "model": "gonzotech:block/third/heavy_door_bottom" },
    "facing=north,half=lower,open=true":  { "model": "gonzotech:block/third/heavy_door_bottom_open" },
    "facing=north,half=upper,open=false": { "model": "gonzotech:block/third/heavy_door_top" },
    "facing=north,half=upper,open=true":  { "model": "gonzotech:block/third/heavy_door_top_open" },
    "facing=east,half=lower,open=false":  { "model": "gonzotech:block/third/heavy_door_bottom", "y": 90 }
  }
}
```
(У нас в репо модели машин уже лежат с `y: 90/180/270` — тот же приём, см. `second_pump.json`.)

**Важное про Blockbench:** экспортировать именно «модель блока» (Java Block/Item), элементы
позиционировать в пикселях 0–16, панель — 3 px (или 8 px для «половинной» толщины), UV — вручную,
чтобы внешняя и внутренняя стороны отличались. Текстуры — 16×16, PNG, без альфы там, где не надо.

## 5. Как дверь ляжет на контур радиации (уже готово)

В `radiation/Containment.java` сегодня реализован Containment 2.0, и заслонки там учтены ровно так,
как ты сказал:

* **закрытая заслонка** замыкает полость (иначе заливка вырвется наружу и контура нет), **но в
  среднем расчёте не участвует вообще** — не тянет фактор к 0.02/1.0 и не отнимает площадь у
  экранирующих клеток;
* заслонкой считается блок из тега **`gonzotech:contour_seal`**; если у блока есть булево состояние
  `open`, заслонкой он считается только при `open=false` (открытая дверь = дырка, контур разомкнут);
* антиэксплойт: если заслонок в оболочке **больше половины**, они считаются обычными стенами
  (иначе «стена из дверей» + один блок вольфрама давали бы бесплатный контур);
* признак «полость замкнута» теперь хранится отдельно (`Containment.isEnclosed`) — это задел под
  **чистую комнату** (у тебя она будет через эффект — жду описания) и под герметичные отсеки.

**Что нужно от двери:** имя состояния `open` (тогда код подхватит её без правок) и одна строка в
теге. То есть дверь сразу начнёт работать как «заслонка», а её открытое состояние — как дырка.

## 6. Наш собственный опыт составных блоков (чтобы не изобретать заново)

В моде **уже есть** два мультиблока, и они сделаны иначе, чем ванильная дверь:

| механизм | как устроен | брать ли для двери |
|---|---|---|
| `SteamGenPartBlock` / `SteamGenCoreBlock` + `SteamGenStructure` (5×5×5, 457 строк) | событийный валидатор: изменение любого блока → пересборка связной компоненты → индекс «часть → контроллер»; ядро в углу помечается `CONTROLLER`, все части — `FORMED` | **Нет** для двери (это поиск структуры), **да** для станка 3×3×2 |
| `TurbinePartBlock` / `TurbineRotorBlock` + `TurbineStructure` | то же самое для турбины | так же |
| **Smart CTM** (`first_turbine_casing_ctm.json`, `second_steamgen_casing_ctm.json`) | `formed=false` → монтажная рамка, `formed=true` → бесшовная панель; стыки считаются по 8 соседям при построении меша | это и есть «структура, определяемая через CTM» — так и надо делать станок: детект структуры + `formed` + `_ctm` модель |
| ванильная дверь | пара блоков по соглашению `HALF` + `updateShape` | **наш случай**: у двери нет «структуры», есть **группа из 4 клеток** — 4 проверки состояний, и всё |

Вывод: для двери индекс структуры избыточен (дверь — не «собранная машина», а один объект из 4
клеток), а для станка 3×3×2 у нас уже есть готовый образец — `SteamGenStructure` + CTM-модель.

## 7. Порядок работ (моё предложение)

| шаг | что | зачем |
|---|---|---|
| 1 | Контур 2.0 (сделан сегодня) | фундамент: чистая комната, ящики, отсеки |
| 2 | **Ты рисуешь 4 модели + 2 текстуры** в Blockbench (или я готовлю JSON-заготовки-плейсхолдеры, чтобы можно было тестировать механику до текстур) | арт — твой |
| 3 | Я пишу `HeavyDoorBlock` + тег + рецепт + ланг (по 4-клеточной схеме) | механика |
| 4 | Чистая комната (по твоему описанию через эффект) + обдуватель | следующая веха базы |
| 5 | Станок 3×3×2: детект структуры по образцу парогенератора + CTM-модель базы | литография |
