# Эпоха III: литография, микроконтроллеры и умные реакторы

**Дата:** 26.09.2026
**Статус:** литография/контроллеры/реактор — план; базовая чистая комната реализована, исправления 0.3.18 ожидают игровой приёмки.
**Основание:** `EPOCH3-BRAINSTORM-2026-09-22.md`, `EPOCH3-BASE-2026-09-22.md`, `UPDATED_TEMP_NOTES.md`, текущий код машин/радиации и закрытая рецептурная модель Эпохи III.

> Главная технологическая цепочка:
>
> ```text
> кремний → пластины → литография → микросхемы → микроконтроллеры
> → умные механизмы → управляемый ядерный реактор
> ```

---

## 1. Цель Эпохи III

Эпоха III не должна быть просто набором более дорогих машин. Её тема — **точность, управление и повторяемость**.

Предыдущая ядерная топка остаётся тепловым источником/горелкой. Литография создаёт первый настоящий слой управления:

- микросхема знает режим машины;
- контроллер открывает автоматические режимы и защиту;
- процессор становится обязательным компонентом сложных механизмов;
- реактор переходит от «топливо греет» к управляемой системе с реактивностью, стержнями, каналами и авариями.

### Что не является целью первой итерации

- не делать сразу все семь семейств реакторов;
- не превращать литографию в GUI-мини-игру;
- не создавать отдельную систему энергии вместо GTU/GTH;
- не делать процессор универсальным ключом от всех машин;
- не вводить мгновенное крафтовое производство микросхем без качества и брака.

## 3. Материальная база

Из заметок закрепляется тройка Эпохи III:

- **алюминий** — корпуса, рамы, радиаторы, кассеты, лёгкие панели;
- **нержавеющая сталь** — вакуум, химия, горячие зоны, корпуса реакторов;
- **никель** — соединения, нагреватели, катализаторы, высокотемпературные элементы.

Спецматериалы:

- **цирконий** — оболочка ТВЭЛов;
- **бор** — поглотители нейтронов и управляющие стержни;
- **литий** — будущие теплоносители/тритий, не обязательный материал первой литографической вертикали;
- **полупроводник/кремний** — активная электронная основа.

Уже созданные `aluminum_housing` и `sheathing` использовать как базовую конструкцию корпусов линии. Их рецепты не переписывать при добавлении функционала.

## 4. Литографическая цепочка

### 4.1. Физический поток

Первая рабочая версия должна сохранять идею заметок: пластина физически проходит последовательные операции, а не просто кладётся в один крафтер.

```text
кремниевый кристалл/сырьё
    ↓
резка пластины
    ↓
шлифовка и полировка
    ↓
окисление
    ↓
нанесение фоторезиста
    ↓
степпер / UV-засветка
    ↓
проявление
    ↓
травление
    ↓
ионная имплантация
    ↓
металлизация
    ↓
разделение кристаллов
    ↓
корпусирование
```

В gameplay это можно реализовать как 8–10 блоков линии. Не требуется делать отдельную сложную машину для каждого химического микрошагa в первой поставке: часть операций допускается объединить в data-driven processing stage, но предмет должен менять стадию и качество.

### 4.2. Предметные стадии

Рекомендуемая последовательность item forms:

1. `silicon_crystal` или существующий кремниевый материал;
2. `silicon_wafer_raw`;
3. `silicon_wafer_polished`;
4. `oxidized_wafer`;
5. `resist_wafer`;
6. `exposed_wafer`;
7. `etched_wafer`;
8. `doped_wafer`;
9. `metallized_wafer`;
10. `microchip_die`;
11. `packaged_microchip`;
12. `microcontroller`/`processor`.

Имена можно скорректировать до начала регистрации, но смысл разделения нужно сохранить: игрок должен видеть, где именно линия дала брак.

### 4.3. Состояние пластины

Не создавать отдельный предмет для каждого сочетания качества. Одна пластина должна нести структурированное состояние:

```text
stage             текущая стадия;
layer             номер/тип нанесённого слоя;
cleanliness       чистота;
alignment         качество совмещения;
yield             выход годных;
impurities        загрязнения;
recipe/profile    профиль будущей микросхемы.
```

Для этого использовать Data Component, а не свободный произвольный NBT. Основа: `ModDataComponents` и паттерн существующих компонентов alloy.

### 4.4. Совмещение слоёв и выход годных

Уникальная механика литографии — не сложная мини-игра, а накопительная инженерная статистика:

```text
yield = base yield × cleanliness factor × alignment factor
```

Базовая идея из заметок:

```text
0.97^10 ≈ 74% без дополнительных штрафов
```

Последствия:

- чистая комната повышает выход годных;
- пыльная/грязная зона даёт больше брака;
- ошибка совмещения одного слоя может испортить весь die;
- плохая пластина превращается в silicon waste/defective die, а не исчезает бесследно;
- высокий tier требует не только дорогих компонентов, но и стабильного процесса.

Не делать случайный шанс единственным объяснением результата: игрок должен получать диагностируемые причины брака.

## 5. Чистая комната и UV

### 5.1. Минимальная механика первой версии

Чистая комната должна быть отдельным условием линии, а не декоративным тегом.

Проверяемые факторы:

- закрытый контур/тамбур;
- отсутствие пылящих производств рядом;
- наличие обдува/фильтрации;
- подходящий корпус и чистые поверхности.

Состав clean-room multiblock и точная геометрия уточняются после первого прототипа, но проверка должна быть серверной и воспроизводимой.

### 5.2. УФ-опасность

Степпер использует UV-засветку. Существующую `PsycheUltraviolet` можно связать с рабочей зоной:

- игрок рядом с открытым степпером получает UV exposure;
- закрытый корпус/защитная обшивка снижает exposure;
- визуальный эффект и HUD переиспользуются;
- процесс не должен требовать постоянного присутствия игрока после запуска.

Важно не делать UV обязательной причиной остановки каждой операции: это должна быть опасность рабочего места, а не случайный softlock производства.

## 5.3. Утверждённая спецификация чистоты воздуха

Ниже фиксируются решения автора для реализации базового clean-room слоя.

### Пылемер

Вне чистого контура прибор показывает:

```text
Качество воздуха: обычное
```

Внутри контура показывает числовое качество `0..100%` с обратной шкалой цвета: малые значения красные, большие зелёные. Та же строка добавляется в отчёт телифона.

### Контур и начальное состояние

Допустимая оболочка чистого контура:

- фарфор;
- кварцевые блоки;
- гермодверь;
- борное стекло;
- `minecraft:white_concrete`;
- другие блоки, которые будут явно добавлены в clean-room tag.

**Уточнение автора и реализация 0.3.18:** узлы всех тиров, очиститель и фильтр тоже
герметичны. Разрешённые белые материалы/гермодверь/приборы задаются тегом
`gonzotech:clean_room_seal`; узлы определяются по классам NodeBlock,
UniversalNodeBlock, UniversalFluidNodeBlock (включая наследников).

Внутри допускаются трубы, провода, composite pipe, все Gonzo-блоки с `third_`
(включая будущие) и `gonzotech:clean_room_interior` (сейчас корпуса/обшивка).
Они обходятся **как внутренний объём**, поэтому не могут заменить стену, пол или
потолок. Земля и прочие неразрешённые блоки внутри делают контур невалидным —
выбран вариант с разрешённым списком. Вода/заболоченные блоки не допускаются.
Проверяются все шесть направлений; предел — 2048 внутренних клеток, включая
допустимое оборудование. Контур может быть непрямоугольным.

Гермодверь всегда разделяет два clean-room объёма — независимо от того, открыта она или закрыта. Это специальное правило чистой комнаты и не заменяет radiation-правила дверей.

Каждая новая топология контура получает:

```text
air quality = 0%
```

Если контур был разгерметизирован и затем восстановлен, он получает новый state и снова стартует с 0%. Старое качество нельзя восстанавливать только по координате комнаты.

Качество едино для всего связного объёма и сохраняется в dimension-level SavedData.
Поставленная внутри труба/third-машина не меняет связность и не сбрасывает качество.
Изменение топологии (например, новая внутренняя герметичная перегородка) создаёт
новое состояние с 0%. Фактическая разгерметизация инвалидирует старое состояние
немедленно, даже если отверстие заделали в тот же тик; обычная выгрузка чанка
только приостанавливает работу. Неизвестные/незагруженные чанки не считаются воздухом
и не подгружаются детектором.


### Грязность игрока

Скрытый параметр игрока:

```text
dirt = 0..100
```

Вне чистого контура:

```text
dirt += 5 единиц/сек, максимум 100
```

В чистом контуре:

```text
dirt -= 1 единица/сек
air quality -= 3 процентных пункта за каждую естественно потерянную единицу
```

Очиститель снимает dirt без дополнительного штрафа воздуху. Выход игрока из комнаты прекращает его влияние на quality.

### Очиститель

Очиститель ставится на пол, направлен вверх и запускается редстоун-импульсом. После фронта редстоуна он 160 тиков (8 секунд) выпускает вверх белые частицы `POOF` с направленной скоростью. Удержанный сигнал и соседские обновления не продлевают импульс.

Игрок считается находящимся в потоке, если:

- абсолютное отклонение X от центра очистителя `<= 0.7`;
- абсолютное отклонение Z от центра очистителя `<= 0.7`;
- разница по Y `<= 3`;
- между очистителем и игроком нет блоков, только `air`.

Эффект активного потока:

```text
dirt -= 11.5 единиц/сек
```

Максимальное снятие за один 8-секундный импульс — 92 единицы. Поток работает и вне замкнутой комнаты; во время обдува у игрока не добавляется наружная грязь и не применяется естественный штраф воздуху.

### Фильтр

Фильтр размещается внутри чистой комнаты, а не в гермобуфере с очистителем. Он имеет:

- отдельный внутренний буфер GTU;
- 3 предметных слота;
- максимум 64 предмета в каждом слоте.

Расход материалов:

```text
уголь: 1 предмет на 60 секунд работы
платиновый или палладиевый самородок: 1 предмет на 180 секунд работы
```

Фильтр восстанавливает:

```text
air quality += 0.2 процентного пункта/сек
```

Фильтр работает только при валидном clean-room контуре и наличии GTU/расходников.
Он ищет комнату по всем шести соседям (в том числе при установке под потолком);
если примыкает к двум разным комнатам — не работает, чтобы не соединять их
производственное состояние. При отсутствии контура рабочие GTU и оплаченный запас
материалов не расходуются, но паразитная потеря GTU продолжается. Предмет списывается **в начале** оплаченного периода 60/180 секунд;
остаток сохраняется в BE, пауза его не сжигает. Это исключает бесплатную работу
через регулярный слом/перестановку до списания.

Уточнение автора для **0.3.20**: буфер **2040 GTU**, максимальный суммарный приём
**32 GTU/т** со всех сторон; очистка **2.6 GTU/т**, паразитная потеря **0.019 GTU/т**
каждый загруженный серверный тик, включая простой. При работе итог **2.619 GTU/т**.
Качество растёт на **0.01 п.п./рабочий тик = 0.2 п.п./с**, материалы оплачивают
ровно 1200/3600 рабочих тиков. Автоматическое извлечение из трёх слотов запрещено;
ручное изъятие и выпадение содержимого при сломе сохранены.
Верхняя полоса 52×16 растёт слева направо по расходу угля, нижняя — справа налево
по расходу катализатора. Подсказки содержат качество воздуха и процент **израсходованного**
материала (30/90 рабочих секунд — 50%). Размеры/координаты — `SUPER_CRUCIAL_FILE.md`.
Сохранённые старые секунды мигрируют в тики; старый GTU-буфер ограничивается новым максимумом.

Внутри комнаты дополнительно разрешены `heavy_weighted_pressure_plate`,
`light_weighted_pressure_plate`, `minecraft:light`, оба сингулярных источника мода.
Это только интерьер: ни один из них не заменяет герметичную стену/пол/потолок.
 Катализатором считается платиновый или палладиевый самородок; точное правило «любой из двух» фиксируется в обработчике рецепта/расхода.

### Открытый воздух и качество производства

Пылемер вне контура показывает `обычное`, но литографическая операция получает специальное production quality:

```text
производство без clean-room контура = 10% качества воздуха
```

Это намеренно отличается от UI-сообщения «обычное»: открытый воздух не является clean-room state, но должен иметь определённый нижний production fallback.

Новая комната стартует с 0%, поэтому свежесозданная, ещё не отфильтрованная комната хуже открытого воздуха. Нелинейная формула брака будет определена после проектирования полной цепочки литографии; до этого clean-room quality хранится и обновляется независимо.

## 6. Какие микросхемы производить первыми

В заметках фигурируют три микросхемы. Рекомендуемый первый набор:

### 6.1. Control Microcontroller

Базовый контроллер:

- автоматические режимы машин;
- запуск/остановка по redstone;
- базовая телеметрия;
- защита от неправильного сырья.

### 6.2. Power Controller

Силовой контроллер:

- управление GTU/GTH;
- ограничения нагрузки;
- приоритеты потребителей;
- аварийное отключение.

### 6.3. Reactor Controller

Специализированный контроллер реактора:

- чтение реактивности;
- управление стержнями;
- аварийный SCRAM;
- телеметрия температуры/давления/нейтронного потока.

### Связь с текущими компонентами

- `transistor` — дискретный электронный элемент;
- `semiconductor_plate/core` — материал активной части;
- `logic_module` — сборочный промежуточный компонент;
- `energy_module` — питание;
- `fluid_module` — сенсоры/клапаны и fluid control;
- `electric_motor` — привод механизмов.

Процессор не должен заменять все эти компоненты. Он собирается из них и открывает именно интеллект/автоматику.

## 7. Переход от процессоров к «умным механизмам»

После появления микроконтроллеров вводится общий machine capability/controller slot:

```text
machine body + processor/controller + energy + fluid/equipment modules
```

### Базовые эффекты контроллера

- машина получает валидный operating mode;
- появляется автоматический input/output;
- становится доступна телеметрия через comparator/HUD;
- аварийные состояния записываются явно;
- без контроллера машина либо ручная, либо ограниченная.

Не нужно сразу переводить все существующие машины на новую систему. Начать с новых smart machines и реактора. Затем точечно добавить controller slot к наиболее важным машинам Эпохи III.

### Профили процессора

Один предмет `microcontroller` с Data Component profile или три отдельных результата?

Рекомендация для первой версии: **три отдельных предмета**, потому что они:

- понятно отображаются в книге и инвентаре;
- дают разные рецепты;
- проще балансируются;
- не требуют сложного NBT-подбора в рецептах.

Позднее можно перейти на программируемый процессор с профилем, если появится реальная потребность.

## 8. Первый реактор после литографии

Не начинать с семи семейств. Первый вертикальный срез — **управляемый твердотопливный реактор**.

### 8.1. ТВЭЛ

ТВЭЛ — item с состоянием:

```text
shell material       zirconium/stainless/etc.;
fuel composition     uranium/MOX/thorium/etc.;
enrichment           enrichment level;
burnup               accumulated burnup;
temperature          optional thermal state;
```

В первой версии достаточно:

- zirconium shell;
- natural/enriched uranium fuel;
- burnup;
- max temperature;
- spent fuel output.

Сложные трансмутации Th→Pa→U-233 и breeding оставить второй волной.

### 8.2. Многоблок

Первый reactor multiblock:

- controller block;
- stainless steel/aluminum housing;
- active channels;
- control rod ports;
- coolant ports;
- heat output port;
- emergency drain/containment.

Переиспользовать паттерн `SteamGenStructure`/`TurbineStructure`: formed state, controller authority, server-side validation, bounded structure scan.

### 8.3. Реакторная логика

Минимальный цикл:

```text
fuel + moderator + control rod position
    → reactivity
    → heat/GTH
    → coolant load
    → radiation risk
```

Состояния:

- shutdown;
- startup;
- stable;
- overheating;
- SCRAM;
- damaged/meltdown.

Интеграция:

- GTH — существующий heat network;
- GTU — существующая energy network;
- вода/пар — существующие fluid paths;
- radiation — `ChunkRadiationData` и placed source/contamination pipeline;
- containment — существующая shielding logic;
- stress/UV/psychology — только если авария реально создаёт воздействие.

### 8.4. Умный реактор

Без `Reactor Controller`:

- ручная ограниченная эксплуатация;
- нет автоматического SCRAM;
- нет полной телеметрии;
- повышенный риск человеческой ошибки.

С `Reactor Controller`:

- управление стержнями;
- автоматический shutdown по температуре;
- аварийные пороги;
- компаратор/HUD output;
- безопасные режимы.

Так выполняется цепочка:

```text
процессор → умная машина → управляемый атом
```

## 9. Порядок реализации

### Волна 1. Основа материалов и данных

- утвердить названия wafer/chip/processor items;
- зарегистрировать chemical supplies литографии;
- добавить Data Component для wafer state;
- добавить item/block models и lang;
- без новых рецептов машин до проверки схемы данных.

### Волна 2. Первый wafer pipeline

- wafer cutting;
- polishing;
- oxidation/resist;
- базовый yield;
- defective output;
- server-side processing и сохранение состояния.

### Волна 3. Stepper и clean room

- clean-room multiblock;
- UV stepper;
- alignment/layer count;
- contamination penalty;
- ограниченный UV exposure;
- smoke test с чистой и грязной комнатой.

### Волна 4. Microchips

- etch/implant/metallization;
- die separation;
- packaging;
- три типа microcontroller;
- рецепты видны по правилам открытия 3;
- компоненты не получают `BOTCHED_MECHANISM`.

### Волна 5. Smart machine API

- общий controller capability/slot;
- validation профиля;
- telemetry/comparator output;
- первая новая smart machine;
- только после этого подключать существующие машины.

### Волна 6. Первый управляемый реактор

- TVEL item state;
- reactor multiblock;
- reactivity/heat/coolant;
- control rod logic;
- Reactor Controller;
- аварийные состояния и radiation contamination.

### Волна 7. Боковые семейства реакторов

Только после игрового smoke-test первой модели:

1. PWR/VVER двухконтурный;
2. быстрый натриевый/свинцовый;
3. ториевый жидкосолевой;
4. волновой;
5. газофазный;
6. импульсный.

Не реализовывать семь семейств параллельно: общий TVEL/reactivity/heat API должен быть проверен на первом реакторе.

## 10. Прогрессия и gates

Сохраняем принятую политику Эпохи III:

- рецепты литографии и микросхем видны в книге после открытия 3;
- компоненты физически можно крафтить до открытия 3;
- только machine-block outputs используют `BOTCHED_MECHANISM`;
- процессоры/микроконтроллеры являются компонентами, а не физически заблокированными машинами;
- reactor blocks и lithography machine blocks получают физический gate как machines;
- найденные варианты рецептов одной микросхемы используют общий `group`, чтобы не засорять книгу.

Рецепт должен иметь:

```text
уникальный recipe id
общий group для альтернатив
один результат
```

Выдача рецептов в книгу должна оставаться централизованной через `TierThreeCrafting`, а физическая подмена результата — через `isGatedOutput`.

## 11. Acceptance criteria первой завершённой вертикали

### Литография

- пластина физически проходит минимум четыре стадии;
- состояние пластины сохраняется при переносе/перезапуске;
- грязная комната повышает брак;
- повторный одинаковый запуск даёт объяснимый результат;
- повреждённая пластина не превращается в полноценный процессор бесплатно;
- UV-риск не создаёт softlock.

### Микроконтроллеры

- минимум три разных типа контроллеров;
- каждый тип имеет собственный профиль и применение;
- `transistor`, `logic_module`, `semiconductor_core`, `energy_module`, `fluid_module` реально участвуют в цепочке;
- альтернативные рецепты группируются в книге;
- компоненты можно производить до открытия 3, если это соответствует текущей политике.

### Реактор

- первый реактор использует существующие GTH/GTU/fluid/radiation systems;
- без controller и с controller поведение различается;
- есть штатный shutdown и аварийный SCRAM;
- перегрев имеет последствия;
- авария может дать radiation contamination;
- multiblock корректно собирается/разбирается и не оставляет stale state.

## 12. Риски и решения

| Риск | Решение |
|---|---|
| 8–12 блоков линии превратятся в непомерный scope | сначала 4 стадии и один stepper, затем расширять цепочку |
| NBT-переменные сломают stack equality | Data Component + per-stack state, без глобального ItemStack equality mixin |
| слишком много случайного брака | показывать cleanliness/alignment и причины через tooltip |
| UV превратится в раздражающий постоянный урон | exposure только возле активного открытого stepper, защита/закрытый корпус |
| семь реакторов создадут семь несовместимых API | первый reactor family как reference implementation, общий core API |
| процессор станет бесполезным предметом | контроллер должен менять реальные operating modes, telemetry и safety |
| реактор станет «ещё одной ядерной топкой» | обязательные reactivity/control rod/coolant/ аварийные состояния |
| чрезмерный GUI | физический поток предметов и multiblock state, GUI только для telemetry/configuration |

## Финальная рекомендация

Начинать не с реакторов и не с полной линии из десяти блоков. Лучший первый vertical slice:

```text
polished wafer
→ resist/exposure stepper
→ etched/doped die
→ control microcontroller
→ один smart machine controller
```

После подтверждения, что этот цикл интересен и стабилен, добавлять:

```text
power/reactor microcontroller
→ TVEL
→ первый управляемый solid-fuel reactor
```

Так процессоры действительно становятся мостом к «умным мехам», а реактор — естественным первым большим потребителем созданной электроники, а не независимой машиной с ещё одним несвязанным ресурсом.
